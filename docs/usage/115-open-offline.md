# 115 Open 离线下载使用与升级说明

本功能为 `115 Open` 离线下载保存 115 返回的原始 `info_hash`，支持从 OpenList API 和任务列表查看，并可在删除已结束任务时选择同时清理 115 云端下载记录及其源文件。新任务的回执独立持久化，不需要开启通用下载任务的 `tasks.download.task_persistant` 配置。

`info_hash` 是 115 接口返回的任务标识，应按原始字符串保存和使用。它不保证等于磁链中的 BTIH、ed2k 文件哈希或下载文件的校验值。`115 Cloud` 是另一种工具，不适用本文新增的回执与云记录清理功能。

## 挂载与下载目录

1. 在管理后台添加或检查 `115 Open` 存储，按现有驱动流程完成授权。确认挂载可用，并能访问计划用于离线下载的目录。
2. 在文件列表打开目标目录，使用离线下载入口，明确选择工具 `115 Open`。调用 API 的用户需要添加离线下载任务的权限，并且可以写入目标路径。
3. 如果最终目标不属于 `115 Open` 挂载，先在后台“设置 → 其他”的 `115 Open` 项目中配置临时目录，即 `115_open_temp_dir`。该值是 **OpenList 内的挂载路径**，例如 `/115-A/OfflineTemp`，必须指向可用的 `115 Open` 存储，不是操作系统的临时目录。

实际提交位置按目标目录决定：

| 最终目标 | 向 115 提交时使用的目录与账号 |
| --- | --- |
| `/115-A/Downloads` 本身位于 `115 Open` 挂载 | 直接使用该目标目录及其挂载账号；不要求配置全局 115 Open 临时目录 |
| `/Local/Downloads`、其他网盘等非 `115 Open` 目标 | 使用 `115_open_temp_dir` 下为该任务创建的独立子目录，云端完成后再创建转存任务 |
| 另一个 `115 Open` 挂载 `/115-B/Downloads` | 直接使用 B 挂载及其账号，不会因为临时目录设在 A 挂载而改用 A |

任务保存的是**实际提交存储的 ID、当时验证的 115 账号 UID 和云端回执**。查询和云记录清理不会只根据目标路径或当前全局临时目录猜测账号。修改全局临时目录不会把已经创建的任务改绑到新目录。

已有任务执行或转存期间，尽量保持挂载路径、存储及账号不变。原存储换账号、停用、删除或替换驱动后，云记录操作会被拒绝。删除原挂载再创建同名挂载会产生不同的存储 ID，不能接管旧任务。只修改原挂载路径时，云记录查询和清理仍可按存储 ID 找到原账号；但任务中保存的临时路径不会自动改写，未完成的转存可能因此失败。

跨存储下载需另外查看“离线下载转存”任务：下载任务成功可能表示已经排入转存任务，不能据此认定目标文件全部传输完成。转存任务仍由原有 `tasks.transfer.task_persistant` 配置决定是否保存；115 下载回执的独立持久化不会替代转存任务持久化。未开启转存持久化时，应尽量等待转存结束后再重启。

添加时的 `delete_policy` 控制转存任务结束后的临时源文件处理，与下文的 `delete_cloud_record` 相互独立：

| `delete_policy` | 跨存储转存时的文件处理 |
| --- | --- |
| `delete_on_upload_succeed` | 对转存成功的源文件尝试删除 |
| `delete_on_upload_failed` | 对转存失败的源文件尝试删除；失败不代表目标已有完整副本 |
| `delete_never` | 不由转存任务删除临时源文件 |
| `delete_always` | 转存成功或失败均尝试删除对应源文件 |

这些策略作用于各个转存任务的源文件，不保证自动删除整个临时目录；文件清理错误会写入日志。直接下载到同一个 `115 Open` 目标目录时不创建转存任务，因此不会因这些策略删除该目录中的下载文件。若需要在跨存储场景保留 115 临时文件，应明确选用 `delete_never`，并核对实际发出的添加请求。云清理确认框中的源文件选择仅作用于该次云记录删除请求，不会覆盖已配置的转存文件处理策略。

## 添加下载并取得原始 info_hash

### 后台操作

在离线下载面板输入链接、选择目录及 `115 Open` 后提交。全部创建成功时，面板关闭并提示已创建数量；部分或全部未创建时，面板保留逐项结果，并显示已创建任务的本地任务 ID。

- “已创建任务”表示 OpenList 已保存并排队处理，115 可能尚未返回受理结果。
- 部分创建失败时，面板保留已创建任务的 ID，并将输入保留为未创建的项目。处理失败原因后，只重试这些项目。
- 如果没有收到响应或响应无法逐项确认，面板会提示结果无法确认，并禁止直接重发当前批次。先打开离线任务列表核对；关闭面板重新填写时，也只提交确认尚未创建的链接。

在管理后台“离线下载”的任务列表展开相应任务，可查看并复制“115 info_hash”，同时查看“115 提交状态”和“云端记录清理”状态。暂时显示“暂无已确认的 115 回执”时，继续查询同一个任务，不需要为了取得 hash 再添加一次下载。

### API 调用

接口沿用 OpenList 身份认证。请求头 `Authorization` 使用当前 OpenList 令牌，`Content-Type` 为 `application/json`。以下路径示例适用于能够访问该挂载的用户；设置了用户根目录时，`path` 按该用户可见路径填写。

添加请求：

```http
POST /api/fs/add_offline_download
```

```json
{
  "urls": ["<下载链接>"],
  "path": "/115-A/Downloads",
  "tool": "115 Open"
}
```

响应中的 `data.tasks` 保留全部已创建任务，`data.results` 按原始 `urls` 的顺序给出结果。`index` 从 0 开始，包含空字符串和空白项的位置。例如，第一项创建成功、第二项未创建时：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "tasks": [
      {
        "id": "<本地任务ID>",
        "tool": "115 Open",
        "info_hash": "",
        "submission_state": "pending"
      }
    ],
    "results": [
      {"index": 0, "task_id": "<本地任务ID>"},
      {"index": 1, "error": "<未创建原因>"}
    ]
  }
}
```

示例省略了其他原有任务字段。添加返回时也可能已经收到 hash，不应假定它始终为空。

OpenList 的业务错误通常也使用 HTTP 200，必须检查 JSON 中的 `code`。115 Open 批量添加至少创建一项时业务码为 200；空数组或全部为空白项为 400；所有非空白链接均未创建时为 500。批量结果不是“全部成功”的保证，需逐项检查 `task_id` 与 `error`。权限、路径和请求格式等整批错误沿用原有错误响应。

使用返回的**本地任务 ID**继续查询：

| 请求 | 用途 |
| --- | --- |
| `POST /api/task/offline_download/info?tid=<本地任务ID>` | 查询单个任务 |
| `GET /api/task/offline_download/undone` | 查询尚未结束的任务 |
| `GET /api/task/offline_download/done` | 查询已结束任务，包括重启恢复的任务 |

115 受理后，单个任务的数据会包含：

```json
{
  "id": "<同一本地任务ID>",
  "tool": "115 Open",
  "info_hash": "<115返回的原始字符串>",
  "submission_state": "accepted"
}
```

`submission_state` 与下载执行状态 `state` 不同：

| 提交状态 | 含义与操作 |
| --- | --- |
| `pending` | 已保存，等待提交；继续查询 |
| `submitting` | 提交意图及账号绑定已保存，正在等待结果；不要重复添加 |
| `accepted` | 已取得原始回执；继续观察执行状态、进度及错误，受理不代表完成 |
| `failed` | 准备阶段或提交前保存失败，或已得到明确的提交拒绝；修复错误后可使用原任务的重试能力 |
| `unknown` | 可能已经提交成功，但缺少可靠回执；原任务禁止自动及手动重投，先到原 115 账号核对 |
| `legacy` | 历史任务缺少可靠回执或账号绑定；不能据此安全重投或清理云记录 |

只有任务创建者和管理员可以查询和操作任务。其他用户与查询不存在的任务一样得到 404。创建者用户已被删除的历史任务仍可由管理员查看，但不会因此自动获得安全重投条件。

重试接口沿用 `/api/task/offline_download/retry?tid=<本地任务ID>`、`retry_some` 和 `retry_failed`，均使用 POST；`retry_some` 的请求体是任务 ID 字符串数组。已知 hash 的任务重试时查询原云任务，不重新提交链接；缺少可靠结果的任务不能通过这些入口绕过限制。显式重试只适用于已结束的 115 Open 任务，已取消任务还要求配置 `tasks.allow_retry_canceled=true`，该配置默认关闭。该开关不会允许 `unknown`、`legacy` 或已进入云清理流程的任务重投。批量重试仍需检查原有返回格式中的逐项错误，不能只看顶层业务码。

## 删除任务与可选的云记录清理

### 后台的四个入口

在已结束的离线下载任务列表中，下列入口使用同一删除确认框：

| 入口 | 处理范围 |
| --- | --- |
| 单条“删除” | 当前任务 |
| 删除选中任务 | 当前选中的任务 |
| “清空” | 当前任务类型下，调用者有权访问的所有成功、失败和已取消任务 |
| 清空成功任务 | 当前任务类型下，调用者有权访问的所有成功任务 |

**清空范围不限于当前页、搜索筛选结果或管理员的“仅显示我的”筛选。** 服务器还可能处理到打开确认框后、请求执行前刚结束的相应任务。需要精确指定范围时，使用单条或选中删除。

“同时删除 115 云端下载记录”每次打开都默认不勾选：

- 不勾选：只从 OpenList 任务列表移除记录。115 Open 的本地删除标记必须保存成功，任务才会移除；正常重启不会使该记录重新出现。
- 勾选：先检查原存储、原账号和可靠回执，再尝试清理 115 云端下载记录，完成本地保存后移除任务。源文件选项未勾选时使用 `del_source_file=0`，保留已下载文件。
- 无可清理的任务时复选框不可用，确认框会说明原因。混合选择时，勾选后不支持清理或操作失败的项目保留，不能将它们视作已经本地删除。

下方的“是否删除源文件”同样默认不勾选，只有云记录选项已勾选且目标支持该能力时才可操作。明确勾选后，向 115 发送 `del_source_file=1`，删除该云下载任务对应的 115 云端文件或文件夹。取消云记录选项会清除源文件选择；再次打开确认框也会恢复默认。跨存储下载应先确认关联转存已经完成，避免删除转存仍需读取的 115 源文件。

提交后逐项查看已确认移除、云记录和源文件删除状态及保留原因。未收到响应不代表失败，也不代表成功；先刷新任务列表核对，再对仍存在的任务发起新的明确操作。新前端连接旧后端、缺少清理能力字段时，不会假定支持云记录清理；服务端未明确提供 `can_delete_source_file=true` 时，源文件选项禁用。

### 取消与删除的区别

运行中列表的“取消”和删除确认框处理不同的事情：

| 操作 | 当前实现的行为 |
| --- | --- |
| 默认本地删除 | 从列表移除并保存删除标记；不取消已经排队或运行的下载，当前执行仍可能提交到 115、查询进度或创建转存任务 |
| 对尚未开始执行的任务取消 | 标记取消，使排队任务不再开始提交；取消状态会保存供重启恢复 |
| 对运行中且已取得可靠回执的任务取消 | 通知当前执行停止；执行进入取消处理时会尝试删除对应 115 云端下载记录，使用 `del_source_file=0`，不请求删除源文件 |
| 对已经结束的任务调用取消 | 不再执行云清理；若云端仍在活动，应到原 115 账号核对和处理 |
| 勾选云记录清理后删除 | 针对已结束的本地任务重新检查绑定和云状态，保存清理结果后才移除本地记录 |

取消接口 `POST /api/task/offline_download/cancel?tid=<本地任务ID>` 的成功响应只表示已调用取消操作，不是云记录已删除的确认。提交在途、无可靠回执、账号异常或网络错误时，不能保证取消已清理云记录，应结合后续任务错误和 115 当前记录核对。取消后若出现持久化错误，应先修复数据库，不能假定取消状态已经可靠保存。`cloud_delete_state` 记录的是可选云清理流程，不是取消操作的回执；需要明确清理确认时，等待本地任务结束后再使用云记录清理入口。

### API 删除

对应接口如下，批量删除的请求体为 JSON 字符串数组：

| 请求 | 请求体 |
| --- | --- |
| `POST /api/task/offline_download/delete?tid=<本地任务ID>&delete_cloud_record=true` | 无 |
| `POST /api/task/offline_download/delete_some?delete_cloud_record=true` | `["<任务ID1>", "<任务ID2>"]` |
| `POST /api/task/offline_download/clear_done?delete_cloud_record=true` | 无 |
| `POST /api/task/offline_download/clear_succeeded?delete_cloud_record=true` | 无 |

省略 `delete_cloud_record` 或使用 `false`，保持原来的本地删除及响应格式：

- 单条本地删除成功返回业务码 200，不附带新的云清理结果。
- 批量本地删除返回业务码 200，`data` 是失败任务 ID 到错误信息的映射；空对象表示没有报告逐项失败。
- 本地清空若中途遇到删除标记保存失败，会保留相应任务并返回错误，但已经成功移除的任务不会回滚。此格式没有新的逐项结果数组，应刷新任务列表核对实际剩余项。

参数只接受单个字面值 `true` 或 `false`；空值、重复参数、其他值及格式错误返回业务码 400，不会退回本地删除。此接口用本地任务 ID 定位保存的云回执，不接受调用者随意传入另一个 hash 代替。

四个入口均支持可选的 `delete_source_file=true|false`，缺省为 `false`。`true` 必须与 `delete_cloud_record=true` 同时使用，否则返回业务码 400。例如：

```http
POST /api/task/offline_download/delete?tid=<本地任务ID>&delete_cloud_record=true&delete_source_file=true
```

选择云记录清理时，只有本地状态为成功、失败或已取消的 `115 Open` 下载任务适用。其他工具、`115 Cloud`、离线下载转存任务均不支持，返回冲突并保留任务。

首次云记录清理会先同步保存清理意图和源文件选择，再查询云端；意图保存失败时不发云请求。只有首次操作确认云记录已完成或失败，才会发送删除请求；完整、可靠的查询确认记录不存在时，未选择删除源文件的请求可完成本地保存和移除。选择删除源文件时，必须收到该选项的明确删除成功回执；云记录不存在本身不能确认文件已删除。云端仍在排队、运行，状态无法识别或查询失败时，不删除本地任务。列表中的 `can_delete_cloud_record=true` 只表示本地条件允许尝试，不代表已经查询过云端或保证删除成功。

已有 `deleting` 或 `unknown` 状态的任务再次清理时，**只查询核对，不再发送云删除**。记录明确不存在且原请求保留文件时，可完成本地移除；原请求要删除文件但未取得成功回执时，返回 `source_file_delete_unconfirmed`，保留任务并显示文件结果未确认。只要同一 hash 仍存在，就返回业务码 409、原因 `cloud_delete_unknown`，保留任务供核对，不能将它当作同一代旧记录继续删除。已确认 `deleted` 的 hash 再次出现时，同样保留任务，原因是 `cloud_record_reappeared`。后续云清理必须保持原请求的源文件选择，改变选择会返回 `delete_option_conflict`。这些保护也适用于进程重启后的恢复。

单条云清理的 `data` 是单个结果；批量和清空的 `data.results` 是结果数组。每项都包含：

```json
{
  "task_id": "<本地任务ID>",
  "local_deleted": false,
  "cloud_state": "none",
  "source_file_delete_state": "none",
  "code": 409,
  "reason": "cloud_task_active",
  "error": "<具体原因>"
}
```

以每项 `code == 200` 且 `local_deleted == true` 判断本地任务已移除；选择删除文件时，还需确认 `source_file_delete_state == "deleted"`。文件状态 `none` 表示未请求删除，`deleting` 表示意图已保存，`unknown` 表示尚未确认，`deleted` 表示 115 已明确确认删除。**批量及清空接口即使全部项目失败，顶层业务码仍可能是 200。** 单条失败会在顶层及该项给出相同业务码；无权访问或任务不存在为 404，状态、类型或绑定冲突通常为 409，云请求及数据库故障为 500。一次批量内重复的任务 ID 复用第一次结果，不会因此多发云删除。

本地记录移除后，再次用相同 ID 调用删除会得到 404，而不是再次返回原删除结果；404 本身也可能表示当前用户无权访问，不能单凭它认定云记录已删除。保留首次操作的逐项回执，必要时到原账号核对。

## 异常与恢复操作

先区分不同的“未知”：添加请求未收到 OpenList 响应时，本地任务是否创建尚未确认；任务的 `submission_state=unknown` 表示提交到 115 的结果未知；`cloud_delete_state=unknown` 或删除结果中的 `cloud_state=unknown` 表示云记录清理结果未知；`source_file_delete_state=unknown` 表示源文件删除未确认，可以与云记录已确认不存在同时出现。不要用重发全部下载链接来解决这些状态。

| 情况 | 建议操作 |
| --- | --- |
| 添加面板未收到响应，或没有完整逐项结果 | 先查 OpenList 的已结束、未结束列表及已返回的任务 ID；仍无法确认时再核对 115 原账号。不要直接重发整批 |
| `submission_state=unknown` | 到实际提交的 115 账号核对已有离线记录及文件。原任务的重试接口会拒绝重投；确认确有必要后，才有意创建新的下载 |
| 已显示 `accepted` 和 hash，但错误提示回执保存失败 | 先处理磁盘空间、权限或数据库连接等持久化问题，保留任务 ID 与 hash，再重试原任务；已知回执会先尝试保存，然后查询原云任务，不重新提交链接。尚未落盘的回执在进程退出后可能丢失，不应以反复重启代替修复 |
| `account_changed`、`storage_disabled`、`storage_unavailable` | 检查原存储是否启用、初始化成功且仍是原账号；恢复原绑定后再试。换成另一账号或新建同名挂载不会修复旧任务绑定 |
| `storage_missing`、`storage_changed` 或 `legacy_task` | 不手工改任务的账号、存储 ID 或 hash 来绕过检查。可在核对原账号后手动管理云记录；不再需要 OpenList 记录时选择仅本地删除 |
| `cloud_task_active`、`cloud_state_unknown` | 云端仍活动或无法可靠判断。等待并核对 115 状态；本地任务失败并不代表云端也已停止。本地已结束时，取消接口不会再发云删除，应在原 115 账号处理后重新清理 |
| `cloud_query_failed`、超时、网络中断 | 保留任务，恢复连接后刷新状态。若清理状态已是 `deleting` 或 `unknown`，下一次清理只查询核对，不再次发送云删除 |
| `cloud_state=unknown` 或 `cloud_delete_unknown` | 删除可能已经生效。对同一任务重试清理只核对云端；原请求保留文件且记录不存在时可完成本地移除，仍存在时返回冲突并保留。到原 115 账号核对和管理云记录，或明确选择仅本地删除；不要为“重新绑定”而添加相同下载 |
| `source_file_delete_unconfirmed` 或文件状态 `unknown` | 云记录消失不能证明文件已删除。到原账号核对对应文件或文件夹，保留原任务和选择；重复清理不会再次删除文件。确认不再需要 OpenList 记录后，可明确选择仅本地删除 |
| `delete_option_conflict` | 云清理已经保存了源文件选择。再次清理时保持原选择，不能通过更改复选框升级或降级旧请求 |
| `persistence_failed`，尤其 `cloud_state=deleted` 且 `local_deleted=false` | 云记录可能已经删除，但本地保存未完成。修复数据库后重试同一任务的清理；不要再次创建下载。服务端仍会先查云端；记录不存在时只完成本地保存 |
| `cloud_record_reappeared` | 先前已经确认清理的 hash 再次出现，可能是新下载。系统会保留它，不继续删除；核对新记录，旧 OpenList 任务可按需仅本地移除 |

云记录清理状态 `none` 表示尚无此流程的清理意图；`deleting` 表示已保存清理意图；`unknown` 表示结果需重新核对；`deleted` 表示已确认删除或不存在，本地移除仍可能未完成。进程中断后，未完成的 `deleting` 会恢复成 `unknown`，启动恢复不会自动重发云删除。

如果云端已经确认删除或不存在，但保存 `deleted` 的数据库写入失败，重启后可能只能从先前的清理意图恢复为 `unknown`。此时的明确重试仍只查询核对，不再次删除同一 hash；不能用重新提交下载来修复本地持久化问题。源文件删除也独立保存：未落盘的成功回执在重启后成为未知，不根据云记录缺失补作成功；已经落盘的文件确认会保留。若结果已保存、只是本地删除标记保存失败，修复数据库后保持原选择继续完成本地清理。旧快照没有源文件字段时按保留文件恢复。

本地删除使用持久删除标记，因此“从列表移除”不等于物理擦除数据库中所有与任务相关的数据。不要为缩小数据库或修复显示而手工删除专用记录、删除标记或旧快照；这会破坏恢复时的去重与防复活依据。

## 旧任务与升级

新版本启动时会在下载 worker 开始前，将通用下载 JSON 快照中的旧 `115 Open` 任务迁入专用记录表，并从通用快照中过滤这些任务。迁移与过滤在同一数据库事务内进行；已有的新记录和删除标记优先，不会被旧快照覆盖。其他工具仍按原有通用持久化配置工作。

旧快照没有可靠保存的云端回执与实际账号绑定时，迁入后显示为 `legacy`。它们可以保留供查看或仅本地删除，但不会根据链接、文件名、路径或当前账号猜测 hash，也不能通过重试重新提交。旧任务原本未持久化、升级时已不在任何可恢复快照中的，无法凭此升级补回记录。

新的已受理活动任务在正常重启后继续使用同一回执查询，不会为了恢复进度再次提交；已结束任务只恢复到列表，不会自动重新执行。中断时处于 `submitting`、尚未持久化可靠回执的任务会保守恢复为 `unknown`。旧快照损坏、专用记录版本不支持或关键恢复写入失败时，启动会报错停止，而不是跳过记录后继续下载；应先保留数据库副本并排查具体错误。

建议按以下顺序升级：

1. 暂停新增下载，尽量等待活动下载及转存结束。记录仍需核对的任务 ID、hash、原挂载及原账号。不要为了准备升级批量点击“取消”，因为取消可能触发云记录操作。
2. 停止 OpenList 服务或容器，确认没有旧进程继续写入数据库。数据库备份应在停止后完成；不要让新旧版本同时连接同一份生产数据启动。
3. 备份当前二进制或镜像标识、运行配置和完整持久数据。使用 SQLite 时，核对实际生效的 `database.db_file` 路径，停止全部写入进程后保留数据库及仍存在的 `-wal`、`-shm` 等相关文件，不手工删去 WAL；使用外部数据库时，用该数据库的备份工具取得一致备份。还应保存服务或容器的配置参数、环境变量及数据卷路径。仅复制默认 `data` 目录不一定涵盖自定义配置、数据库或本地临时文件路径。配置和备份含存储授权等信息，应保留原来的访问限制。
4. 使用匹配个人前端的后端产物。构建方法见[个人 115 版本构建](../development/custom-115-build.md)；核对 `openlist.build-info` 的前后端完整 SHA，正式交付应为 `backend_dirty=false`。运行配置的 `dist_dir` 留空时才使用嵌入前端；若设置了外部目录，核对它是否仍指向旧界面。不要混用下载官方前端的上游构建入口来验证个人界面。
5. 启动一个新版本实例，检查启动和迁移日志、挂载账号、任务列表及历史任务状态。浏览器刷新后确认可以看到新增回执字段和删除选项；没有选项时先核对前后端版本。
6. 用明确的测试链接与目录完成下节验收，再恢复日常下载及批量清理。

**不承诺将升级后的数据库交给旧版本可无损降级。** 旧版本不了解新专用记录及删除标记；迁移后通用快照中的 115 任务已被过滤，直接更换旧二进制可能看不到新任务，也无法正确处理这些回执和清理状态。

需要回滚时，先停止新版本并备份当前数据，再采用与升级前备份匹配的旧二进制或镜像、配置和数据库。恢复升级前备份会丢失备份之后的本地任务变化；115 云端已经发生的下载、删除以及文件操作不会被数据库回滚撤销。重新开始下载或清理前，应先核对这一时间段的云记录和文件，不能把旧备份当作云端现状。

## 真实验收边界

目前的实现、源码核对和模拟回归不能替代真实 115 验收。**截至本说明编写时，尚未用真实 115 账号完成新增功能的全流程验收，未确认真实云记录删除后的文件保留结果。** 发布或自用前，仍需针对明确的测试任务核对：

- 使用 115 实际支持的测试链接提交，比较 115 返回的原始 `info_hash` 与添加后查询、后台复制的值；磁链与 ed2k 分别验证，不推断所有链接格式都被 115 支持。
- 重启后查询同一本地任务，确认 hash、账号绑定和执行状态恢复，并确认没有重复提交。
- 分别验证后台及 API 的默认本地删除和四种可选云清理入口；云清理后不仅查任务列表，还需到 115 确认对应下载记录消失、已下载文件仍在。
- 验证多挂载、活动云任务、账号变更、网络未知及持久化失败时的保留和恢复操作。使用隔离测试环境注入故障，避免直接破坏日常数据库或凭据。
- 跨存储场景另外核对转存任务、目标文件及原有临时文件删除策略；不能用下载父任务成功替代转存验收。

115 删除接口仅接收 hash，没有任务代次或“状态仍满足才删除”的条件参数。本进程会协调同账号的提交与清理，但无法阻止其他客户端在查询后、删除前重新创建相同 hash 的任务。实际操作时避免其他客户端同时对同一下载反复提交或清理；本功能不保证跨客户端原子条件删除。

字段和完整响应约定见 [115 Open 离线下载 API](../api/115-open-offline.md)。实际验收结果应以所用前后端版本及测试记录为准。
